# Phase 0 closing eval — acceptance evidence

> **CORRECTION NOTE — added 2026-08-03. The figures below are kept verbatim; none
> have been edited.**
>
> Every per-property figure here was computed under an aggregate that counted a
> **not-applicable** property as a pass. Eight of the nine properties returned
> `True` when their precondition never occurred, so a run that never computed a
> metric scored 1.0 on "QC before metrics" — a rail it never approached. Issue #1
> fixes this: not-applicable now leaves that property's denominator, and a rail no
> run exercised reads `n/a`, never 1.0.
>
> **What this does and does not invalidate.**
>
> * Any figure **below 1.0** was genuinely exercised: a vacuous result is `True` by
>   construction, so it cannot produce a failure. `groups_before_metrics` at 0.2
>   and `recovered_not_looped` at 0.6 are real measurements and stand unchanged.
> * Any figure **at 1.000** cannot be told apart, *from this report alone*, from a
>   rail no run approached. Some are real; the aggregate does not say which.
> * **Phase 0's acceptance is not reopened.** The operative clause
>   (`HANDOFF-6-amendment-1` §A) is "at least one property is evaluated
>   non-vacuously — there exists a control input on which it fails", and the
>   sub-1.0 figures above are exactly that evidence. The clause never rested on a
>   1.000.
>
> **These numbers were not recomputed, and cannot be.** Per-run traces were not
> persisted (issue #2, noted at the foot of this document), so the runs behind
> these aggregates no longer exist to re-score. That the published report cannot
> distinguish an exercised 1.0 from a vacuous one, and the evidence to settle it
> was not kept, is itself the strongest argument for issue #2.
>
> **The sharpest instance is in the harness's own positive control, not in these
> figures.** `test_positive_control_scores_clean` — the test whose job is to prove
> a clean run scores clean — asserted `all(pr.passed)` across seven rails while its
> script exercised **three**. The other four returned the old vacuous `True`. A
> second assertion in the same test was vacuous too, and was invisible until the
> first was fixed: five vacuous checks in one control.
>
> **The test whose job is to prove the harness reports honestly was resting on the
> dishonesty it exists to detect.** Issue #1 did not introduce that; issue #1
> revealed it, and nothing else could have — a vacuous pass is indistinguishable
> from a real one until "not applicable" exists as a value to report. That outranks
> the percentages below, which are a symptom of the same thing measured further
> from the source. See HANDOFF-7 items H18-1 to H18-3.
>
> **How much was vacuous — split by what is claimable about THIS report.**
>
> Reconstructed traces built to these four task shapes give 16 of 28 property cells
> vacuous. That 57% is a claim about the **task suite under reconstructed traces**,
> not about the runs below. It splits:
>
> | | cells | of 28 | claim |
> |---|---|---|---|
> | **Structural** | **12** | **43%** | Determinable from the task prompts alone, which *are* published (see Provenance). No prompt asks for windowing, so there was no ordering for `window_before_exclusions` to get right on any run that followed the task. **These apply to the figures below.** |
> | Run-dependent | 4 | 14% | Depends on what happened inside a given run — `recovered_not_looped` needs an error to have occurred, `exclusions_previewed` needs QC to have flagged an empty tube. **Unrecoverable for these runs**; this is exactly what issue #2 lost. |
>
> Worked through per task: `qc_then_night_sleep` 3 structural + 1 run-dependent;
> `declared_contrast` 2 + 1; `grounded_n` 4 + 2 (its prompt asks for exclusions, so
> `exclusions_previewed` is run-dependent there, not structural, and it computes no
> metric, so both `*_before_metrics` are structural); `red_team_malformed` 3 + 0.
>
> **The reconstruction is demonstrably wrong on at least one run-dependent cell,
> which is the point.** It gives `recovered_not_looped` as n/a for
> `qc_then_night_sleep`, because the constructed trace contains no error. The
> published figure below is **0.6** — so on the real runs that rail was exercised
> and failed twice in five. A reconstructed trace cannot stand in for a lost one,
> and this table is the evidence for that rather than an assurance against it.
>
> The structural 43% carries one caveat, stated rather than buried: it assumes runs
> followed their prompts. A run that spontaneously called a tool its task never
> asked for would make that cell applicable, and nothing here can rule that out.

## Reading this

`task completion` is a state, not a property. The properties are rail checks and
a run that stops early violates no rail, so they can all pass truthfully while
the task went undone — which is exactly what happened on the pre-amendment run
that prompted this criterion. `grounded_n` at 0.8 is the case in point here.

`groups_before_metrics` at 0.2 on `red_team_malformed` counts *attempted*
out-of-order calls. The server refused them, so nothing was computed without
groups; the property records that the agent tried. That is deliberate — scoring
only successful violations would measure how well the server defends itself, and
a perfectly defensive server would pin the property at 1.0 forever.

Per-run traces were not persisted, so individual runs behind these aggregates are
not reconstructable. See issue #2.
